# SDK 1.0 integration foundation

This branch replaces developer-authored Edge routing with App → Workspace → Session references. The Edge API remains deployed and is generated by the SDK protocol. Backend code calls the App Edge API, never private platform APIs. The package is `1.0.0-alpha.0`; production rollout still requires coordinated CLI/platform work.

There are two boundaries:

1. **App ↔ Edge:** versioned commands specifying Workspace, Session and operation.
2. **Edge ↔ Sandbox:** the existing actor transport, reached through dispatcher/outbound Worker/broker/gateway infrastructure. Changes to priority scheduling, cancellation attribution and durable views must be negotiated there; the public envelope is not an actor message payload.

## Backend interface

```ts
import { createApp } from "@cantelop/sdk";

type Message = { prompt: string };
type Event = { text: string };
type Reply = { answer: string };
type View = { entries: string[]; inbox: string[] };

const app = createApp<Message, Event, Reply, View>({ edgeUrl, accessToken });
const workspace = app.workspace({ slug: "customer" });
const session = workspace.session({ id: "conversation" });
const message = await session.dispatch({ prompt: "Review the change" });
const steering = await session.steer({ prompt: "Focus on authentication" });
await message.status();
await session.cancel(steering.id);
const view = await session.view();
for await (const event of session.stream({ after: view.cursor })) {
  // Apply application events after the snapshot's atomic boundary.
}
await session.stop();
```

The fourth generic is application view state. Dispatch and steer both accept the first generic and return `MessageRef` with ID, accepted timestamp and status lookup. The former separate steering generic and session-wide `abort()` are removed.

References remain lazy. Session IDs remain App-scoped; omitting one generates it immediately. ID/slug Workspace selection is unchanged. Explicit Workspace resolution is memoized per reference, concurrent database calls share its handle, and failures can be retried. Session commands carry the selected Workspace directly; their Edge handlers own provisioning or read-only lookup.

The normal factory accepts HTTPS `edgeUrl` and an App-scoped `accessToken`, disables redirects, and supplies Bearer authentication. HTTP loopback is permitted for local development. An explicit `AppConnection` is retained for tests/local CLI adapters and receives logical Edge requests at `https://edge.cantelop.internal`. Integration credential issuance, rotation/revocation and URL discovery remain platform follow-ups; account deployment credentials are not integration tokens.

## Common command envelope

All operations use `POST /__cantelop/app/v2/commands`, including streaming. `CANTELOP_INTEGRATION_PROTOCOL_VERSION` is 2; this replaces the earlier alpha's incompatible route-based protocol 1.

```json
{
  "protocolVersion": 2,
  "id": "msg_0123456789abcdef0123456789abcdef",
  "workspace": { "slug": "customer" },
  "session": { "id": "conversation" },
  "command": {
    "type": "steer",
    "message": { "prompt": "Focus on authentication" }
  }
}
```

`workspace` contains exactly one ID or slug. `session` contains the App-scoped ID. `id` is the submission identity for dispatch/steer/request, and the operation identity for other commands. Workspace-level commands use `session: null`. Unknown commands, unsupported fields, invalid selectors/IDs/cursors and input over 1 MiB fail before private routing. The shared fixture is `test/fixtures/integration-v2.json`.

| Command | Fields | Edge behavior |
| --- | --- | --- |
| `dispatch` | `message`, optional `keepAliveSeconds` | Resolve/provision Workspace; admit normal-priority actor message; activate if needed |
| `steer` | `message`, optional `keepAliveSeconds` | Same admission with priority enforced at actor scheduling boundaries |
| `request` | `message`, `timeoutMs`, optional `keepAliveSeconds` | Normal message admission plus existing bounded reply wait |
| `cancel` | `messageId` | Cancel the specific submission; no Workspace provisioning or Sandbox activation |
| `status` | `messageId` | Read the original message receipt without activation |
| `stop` | none | Release current Sandbox; preserve reusable Session identity |
| `stream` | optional `after: { streamId, sequence }` | Read SSE events without activation |
| `view` | none | Read last committed application projection without activation |
| `workspace.resolve` | none | Open/provision a slug or retrieve a canonical Workspace |
| `workspace.database` | none | Obtain renewable managed database credentials |

Each operation has its own Edge handler. There is no client-selected private path or URL. Authentication happens before parsing/routing. The Worker strips client authorization and identity headers; the outbound Worker derives trusted App identity. Private handlers must enforce App ownership and Session/Workspace binding on every operation, including reads and cancellation.

## Admission, priority and keep-alive

Dispatch queues behind normal work when busy. Steer takes priority over queued normal messages at the next safe scheduling boundary, with FIFO ordering within each priority. It does not forcibly interrupt a running handler. Idle steering admits the same message normally. No separate control payload or provider-specific steering schema is introduced.

Keep-alive is optional on the Session reference and on dispatch/steer options. A method value overrides the reference value; omission delegates to the App default. Edge resolves that default from reserved `CANTELOP_DEFAULT_KEEP_ALIVE_SECONDS`, supplied by the platform/local CLI. It fails closed before provisioning if the default is missing/invalid. Explicit zero is preserved. Existing keep-alive/quiescence lifecycle rules remain owned by the actor platform; control/read operations do not renew a lease.

The Edge translates submissions into private integration-v2 admission (`messages` or `requests`) with the existing `{ session, message }` actor data plus enforced `priority: "normal" | "priority"`. Request additionally supplies `timeout_ms`. These are new private admission contracts requiring platform support, not a silent fallback to the old FIFO endpoint. The gateway must negotiate actor support before delivering priority work.

Acceptance means durable admission, not completion. Successful `receive()` still acknowledges intake; application work can outlive it. Caller timeout/disconnect ends waiting without proving execution stopped. Dispatch/steer accept an optional stable `id` for retries; request retains its retry options. Ambiguous failures expose the identity via `RemoteAppError.messageId`, with `command_outcome_unknown` for transport uncertainty. No operation is automatically retried. Platform admission must deduplicate same-ID/same-command/same-payload retries and reject conflicting reuse, including dispatch-versus-steer changes.

## Message-targeted cancellation

`session.cancel(messageId, { id?, signal? })` returns `{ messageId, state, status? }`. `requested` means cooperative cancellation was admitted; `cancelled` means queued work was withdrawn; `settled` reports an existing terminal message outcome in the required `status` field. Unknown targets are errors. A cancellation operation's retry ID is separate from its target ID.

The platform must serialize cancellation against admission/start/settlement, persist withdrawal so recovery cannot resurrect queued work, and retain completed outcomes. Running cancellation must follow ownership from message intake to activity and descendants, even after intake was acknowledged. Shared work cannot be attributed by merely canceling whichever activity happens to be running. Canceling a steering contribution does not undo already-applied effects or automatically cancel an unrelated parent run.

Private cancellation/status/stop/view/events routes are under `/__cantelop/integration/v2/sessions/{id}` and carry exactly one Workspace selector in their query. Cancellation targets `/messages/{messageId}/cancel`; its body carries the cancellation command ID. Read/stop handlers must resolve slugs read-only. Stop retains existing errors for unmaterialized Sessions and permits later reactivation; it is distinct from message cancellation.

## Durable application view

`SessionView<View>` contains `revision`, `updatedAt`, typed `state`, and an atomic event `cursor`. The wire snapshot also contains matching `sessionId`, canonical `workspaceId` and `protocolVersion`. The SDK validates identities, timestamp/revision and cursor metadata; application schemas own validation of `state`.

This is inspired by [pi-durable's committed conversation views](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#watching-a-conversation): transcript and current work are projected as committed state. Cantelop does not require Pi's state shape or Chord operations. Allocation diagnostics belong to a separate platform inspection surface; they are not fabricated as application view state.

Required runtime/platform support:

1. A typed publication primitive/adaptor that commits a bounded application projection, including schema/version ownership. A Pi adapter can publish its conversation view.
2. Durable projection storage keyed by App/Workspace/Session, outside the live process and readable without mounting/starting a Sandbox. Empty/unpublished views return an explicit `view_unavailable` error; stopped Sessions may retain their last committed view.
3. Monotonic revision and event cursor committed atomically with the projection. The initial snapshot plus subscribing after its cursor must not miss concurrent updates. Application state changes must publish corresponding events; generic output alone cannot reconstruct arbitrary state.
4. Writer incarnation checks that reject updates from replaced Sandboxes, authorization on reads/writes, and bounded snapshot/event sizes.
5. Explicit replay expiry/reset behavior, slow-consumer bounds, and snapshot refresh after reconnect gaps. Do not claim exactly-once delivery or application durability from transport acceptance alone.

The SDK does not currently supply the runtime publication primitive or external view store; this PR qualifies the public contract and Edge routing. Current runtime artifacts advertise `priority`, `messageCancellation` and `durableView` as false until these implementations and recovery tests exist.

## Streams

POST streaming returns SSE with existing `{ stream_id, sequence, session_id, message_id, created_at, data }` event envelopes. The SDK maps them to `{ cursor, sessionId, messageId, createdAt, data }`. Parsing handles incremental UTF-8, LF/CR/CRLF, multiline data and heartbeats with 1 MiB line/frame bounds. Malformed identities/sequences/UTF-8 fail. Explicit cursor resumption preserves stream reset/expiry errors; there is no automatic reconnect or agent restart. Ending iteration or aborting its signal closes only the subscription.

## Generated artifacts and rollout

CLI build protocol 6 generates `worker.mjs` plus `cantelop-edge.json` with `buildEdgeApi({ outdir, runtimeOrigin? })`, and `session-runtime.mjs` plus `cantelop-runtime.json` with `buildSessionRuntime({ entrypoint, outdir, projectRoot? })`. Both advertise integration protocol 2; the native actor runtime protocol remains 2. The Worker requires `CANTELOP_INTEGRATION_TOKEN`; optional keep-alive requires the configured App default binding. Local bridge overrides must be numeric HTTP loopback origins.

Project schema 3 has no customer API entrypoint. The CLI must build/upload both artifacts, retain dispatcher/outbound routing and Worker environment/secrets synchronization, and update init, doctor, dev, watch, dry-run and deploy. Existing CLIs must reject this prerelease before upload; published 0.x SDKs remain the legacy deployment path. Schema discovery/watch starts at the project or Session entrypoint and adding an absent schema file requires a watcher restart.

The platform must implement private integration-v2 admission/read/cancellation routes, credentials/defaults, actor capability negotiation and durable view storage before production rollout. Existing Node/Bun runtime behavior is preserved in this foundation rather than advertising unsupported new capabilities.

Webhook handlers, provider signature validation, delivery deduplication and provider acknowledgment belong to the customer's own app. They invoke these same primitives. No SDK Edge webhook routes, provider adapters, managed trigger configuration or platform webhook rollout are planned.
